## M9-A 编码能力 · 已完成

| 项 | 实现 | 口径 |
|---|---|---|
| AV1 | `VideoCodec` 增加 `'av1'`；软件走 **libaom-av1**（随包 FFmpeg 自带；SVT-AV1 属可选升级）；硬件支持 `av1_nvenc / av1_qsv / av1_amf` | `-crf` + `-cpu-used`（x264 preset 名 → 0–8 粗映射，`aomCpuUsed`） |
| CRF 直给 | `MediaBasisOverlayInput.crf` / `ExportRequest.overlay.crf` | 缺省仍按画质档（high 18 / standard 23 / small 28）；传值即覆盖 |
| x264 preset | `encoderPreset` | 缺省 `medium`（与旧 argv 一致）；AV1 映射到 `-cpu-used` |
| 10bit | `bitDepth: 10` → 输出 `-pix_fmt yuv420p10le`，且滤镜链尾落到 `format=yuv420p10le`（M9-B） | UI 侧 H.264 禁用 10bit（x264 8bit 构建不支持）；HEVC/AV1 有效 |
| colorRange | `colorRange: 'full'` → `-color_range pc` + 链尾 `scale=in_range=limited:out_range=full`（M9-B 真转换） | 缺省 limited，不追加参数（argv 与旧版逐字节一致） |
| 三处编码出口 | 四个 overlay builder 统一走 `overlayEncodeArgs()` / `overlayColorArgs()` | **不传 M9 字段时 argv 与旧版完全一致** |
| 产物校验 | `verifyOverlayMp4(..., { videoCodec, bitDepth, colorRange })` | 10bit 校验 pix_fmt；显式 codec 校验 h264/hevc/av1；full range 校验 `color_range=pc` |
| 引擎透传 | `engine.ts` 解析 av1 硬件编码器 + 透传 crf/preset/位深/范围 | 硬件失败仍回退软件编码（旧逻辑不变） |
| UI / CLI | 导出面板编码格式增加 AV1；高级模式增加 CRF / 位深 / 色彩范围；`export.start` 增加同名参数 | 缺省不落键 |

**HDR：本轮未接线（诚实记录）**
- 导入侧按规格 §6.2 把 HDR 素材阻断/转 SDR，导出链固定 BT.709 标签，因此不存在"伪 HDR"输出；
- `hdr: passthrough/tonemap` 需要 10bit 图内处理 + HLG/PQ 传递标签 + 源色彩元数据保留，属于**独立链路改造**（规格变更），本轮不做，避免半成品把 SDR 内容包进 HDR 容器。

## 取证

```
npx vitest run tests/encodingDelivery.test.ts
# 10 例全绿：
#   argv 层 8 例（libaom-av1 参数/旧 argv 不变/硬件 AV1 三个族/codec 不匹配回退/默认无 10bit·range/CRF+preset/10bit+full range/硬件透传）
#   真机 2 例：libaom-av1 产出 codec=av1；libx265 10-bit 产出 pix_fmt=yuv420p10le
```

真机用例用随包 FFmpeg 现场编码 320×180 0.3s 素材再 ffprobe 断言，编码器缺失时自动跳过（不假绿）。

**已知取舍**
- AV1 软件编码用 libaom（essentials 自带），速度明显慢于 SVT-AV1；如需速度可后续加 `libsvtav1` 探测分支；
- 10bit 是"交付路径"：链尾升到 `yuv420p10le` 再编码，但**源素材仍是 8bit**（HDR 传递链路未做），
  不等于原生 10bit 采集；对交付兼容性与后续 HDR 改造是必要基础；
- full range 现在做真转换（`scale=in_range=limited:out_range=full`）+ 标签，不再只是贴标签（M9-B）。

## M9-B 10bit 图内处理 + full range 像素转换 + AV1 回退 · 已完成

| 项 | 实现 |
|---|---|
| 链尾像素格式 | `ffmpegArgs.outputPixelFormat(bitDepth)`：缺省 `yuv420p`（与旧 argv 逐字节一致），10bit 时 `yuv420p10le` |
| 链尾范围转换 | `fullRangeFilter(colorRange)`：`full` 时 `scale=in_range=limited:out_range=full`（**标签不等于转换**：`-color_range pc` 只是标签，不转像素值会让播放器把 limited 像素当 full 解，画面对比拉开） |
| 统一链尾 | `outputTailFilters({bitDepth,colorRange})` 用在三条最终出口：`subtitleOverlayChains`（aboveMedia / belowMedia 两支）、`buildWatermarkFilterChain`、以及多轨基座经 subtitle 链的最终格式；8bit/limited 时字符串与旧版完全一致（81 例 argv 快照锁定） |
| 透传 | `buildFilterComplex(..., color?)` 新增可选参数；`buildOverlayMp4` / `buildOverlayMp4DirectPipe` 从 `OverlayInput.bitDepth/colorRange` 透传；`MediaBasisOverlayInput` 的多输入 builder 直接读同名字段 |
| AV1 回退 | `shared/gpu.softwareEncoderName(codec)`：av1 → `libaom-av1`、hevc → `libx265`、h264 → `libx264`；`overlayMp4` 硬件失败回退的**提示文案**改用同一映射（之前 AV1 会被写成"回退 libx264"，虽然实际编码参数由 `videoEncodeArgs` 按 codec 选对了，文案与行为不一致） |

**口径边界（诚实记录）**：源素材仍是 8bit（HDR 传递链路未做），所以这是"10bit 交付路径"：
链尾升位深 + 范围转换 + 10bit 编码，并不是"原生 10bit 采集/传递"。HDR（HLG/PQ 元数据保留）仍需独立链路改造。

**取证**

```
npx vitest run tests/encodingDelivery.test.ts
# 14 例全绿（原 10 + M9-B 新增 4）：
#   链尾纯函数：缺省与旧版逐字节一致 / 10bit / full+10bit 组合 / full 才追加范围转换
#   滤镜图接线：多输入直接管道 argv 的 filter_complex 里出现 format=yuv420p10le 与
#              scale=in_range=limited:out_range=full；`-pix_fmt yuv420p10le` / `-color_range pc` 齐全；
#              缺省 argv 不出现 -pix_fmt（旧路径不变）
#   回退映射：av1 → libaom-av1 / hevc → libx265 / h264·undefined → libx264
#   真机：`-vf "scale=in_range=limited:out_range=full,format=yuv420p10le"` + libx265 → 产出
#         codec=hevc、pix_fmt=yuv420p10le（随包 FFmpeg 缺编码器时自动跳过，不假绿）
npx vitest run tests/ffmpegArgs.test.ts
# 81 例 argv 快照全绿（证明 8bit/limited 默认路径零回归）
```

## M9-C 4K60 吞吐回归 · 已实测（CLI 路径）

用真实 CLI 叠加出口跑 4K60 2s（120 帧）合成，验证"体积/磁盘门禁 + 帧数/编码参数"链路不退化：

```
node scripts/smoke-export.mjs --overlay --width 3840 --height 2160 --fps 60/1 --seconds 2
# SMOKE PASS，耗时 10.7s（本机 Windows 11 / 随包 FFmpeg 9）
#   OK 帧率 = 60/1        OK 色彩范围 = tv      OK alpha 均值（应 <250）= 14.69
#   OK 宽度/高度跟随参考 = 3840×2160            OK 像素格式回到 yuv420p
#   OK 视频编码 h264      OK 音轨保留（-c:a copy）
#   OK 整条时间轴透传（帧数一致）= 120
```

**口径**：这是 **CLI（无 Electron）** 的真实 FFmpeg 合成路径，覆盖 argv/帧数/编码/磁盘；应用内
4K60 2s 冒烟（真实渲染进程逐帧送帧）在 `npm run verify:all` 里作为独立步骤常跑。
4K60 60fps 下约 5.4 帧/秒的合成吞吐（120 帧 10.7s，含进程启动与编码），满足交付节奏预期；
此数值随机器/编码器变化，只作为"没有数量级退化"的基线。
