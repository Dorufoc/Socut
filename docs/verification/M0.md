> 素材谎报为预乘，避免在 10-bit YUV 等路径上出问题），而非可观测的混合差异。

## M0-8 帧吞吐与 IPC · 通过（应用内真实管线实测）

`FOCUSNEWS_SMOKE=1` 启动开发实例即走**完全相同的真实导出管线**（预设 → Yoga → renderFrame →
原生分辨率 OffscreenCanvas → 帧字节 → IPC → 主进程 stdin → ProRes 4444 → ffprobe 交叉校验），
报告写入 `spikes/app-smoke/report.json`。帧通道仍由主进程 pull 驱动（只有写盘成功才请求下一帧，
序号严格递增），只是传输层换成普通 IPC（见 C16）。

实测（1920×1080 @ 30fps、10 秒、300 帧、两个片段 + 中间间隙）：

| 项 | 值 |
|---|---|
| **总耗时** | **7.13 秒**（验收第 2 条要求 ≤ 30 秒） |
| 吞吐 | 42.1 fps 等效 |
| `renderFrame` 绘制 | 68.7ms 合计 = **0.23 ms/帧** |
| 取帧（getImageData）+ IPC 拷贝 | 1530.9ms = 5.1 ms/帧 |
| 其余（FFmpeg 启停 + ProRes 编码 + 管道 + 产物校验） | ≈ 5.5 秒 |
| 产物 | `ap4h` + `yuva444p12le` + 300 帧 + `30/1` + `tv` ✓ |
| 复跑 | 1080p30/10s 二次实测 6.89s（一致） |
| 4K 上限参考 | 3840×2160 @30fps、2 秒（60 帧）= 6.31s → 外推 4K60/10s 约 25–31s，
  止于此仍能入 30s 线附近；因此 4K 导出仍必须保留体积预估 + PNG 序列/低并发出口（规格 §2.3） |

两条直接导致代码修正的发现：

1. **C16 传输层**：计划里的 `MessageChannelMain` + `webContents.postMessage` 端口方案，在
   `contextIsolation` 下端口要经 contextBridge 二次代理，实测**第 0 帧得不应答**（帧超时）。
   改为普通 IPC：主进程 `export:frameRequest` 拉帧 → 渲染侧 `export:frameResponse` 回传字节；
   代价是每帧一次结构化克隆拷贝，而**背压、不丢帧、序号递增完全保留**。
2. **C17 PNG 压缩是吞吐瓶颈**：360p 下 `convertToBlob('image/png')` 平均 9.7ms/帧，而绘制只要
   0.14ms/帧；按像素线性放大到 1080p 会卡在 30 秒验收线。主路径因此改为**未压缩 RGBA 帧流**
   （`-f rawvideo -pix_fmt rgba -video_size WxH`），渲染侧启用 `willReadFrequently` 强制 CPU 画布
   避开每帧 GPU→CPU 回读，并加入并发窗口（默认 3，受 4 个画布的缓冲池约束）。
   PNG 仍作为 `pipeTransport='png'` 与 PNG 出口/回退保留，UI 可直接切换；
   同尺寸取帧+传输从 579ms 降到 47ms。这正是计划风险表「导出侧降级 rgba8」的具象化。

## 验收第 8 条（取消后无孤儿进程、临时文件已清理）· 通过

取消专用冒烟场景：`FOCUSNEWS_SMOKE=1 FOCUSNEWS_SMOKE_CANCEL=1`（1080p、20 秒时间轴共 600 帧，
渲染侧交付若干帧后主动取消）。主进程在渲染侧上报后交叉校验下列四项，**退出码 0 即全部通过**：

```
{
  "scenario": "cancel",
  "framesDoneBeforeCancel": 20,          // 取消确实发生在中途（共 600 帧）
  "errorCode": "CANCELLED",              // 不是误报为 EXPORT_FAILED
  "activeChildJobs": [],                 // 子进程注册表已空，无孤儿 FFmpeg
  "artifactExists": false,               // 半成品 MOV 已删除
  "staleTempDirs": [],                   // 临时工作区已清空
  "passed": true, "failures": []
}
```

过程中修掉两个真实缺陷：

1. **取消被当成失败**：取消会 reject 在飞帧请求并引发 stdin EPIPE，引擎原先一律走 `fail()`，
   UI 会弹出不该出现的“导出失败”。现在 `runTransparentMov` 与引擎 catch 都会先识别
   `isCancelled()` 并走 `cancelled` 收尾（任何阶段已请求取消都按取消处理）。
2. **半成品未删除**：取消/失败后 `spikes/app-smoke/app-smoke-1920x1080.mov` 仍残留在磁盘上。
   现在 `runJob` 的 `finally` 中只要 `state.phase !== 'done'` 就删除产物（PNG 出口递归删目录），
   日志可见：`已删除未完成产物（cancelled）：…\app-smoke-1920x1080.mov`。

另：冒烟现在会把任何未捕获异常也上报（`SMOKE_EXCEPTION`）并落盘，避免“卡住且无原因”这种调试死角。

## 本轮新增的两条修正（对计划的补充）

| # | 事实 | 处置 |
|---|---|---|
| **C10** | `ffmpeg` 与 `ffprobe` **都没有 `-nologo` 选项**：传入直接 `Unrecognized option 'nologo'` 并退出（本机 FFmpeg 8.1.1 实测）。计划/规格未提及，但它会让所有导出命令在启动瞬间失败 | `ffmpegArgs.ts` 的前缀参数改为 `['-hide_banner', '-y']`；`tests/ffmpegArgs.test.ts` 断言 argv 不含 `-nologo`；`ffprobe` 的 `-nologo` 同样会在探测阶段吞掉文件名 |

## 工程结构交付物补齐（本轮审计发现的两处缺失）

### 1. `resources/icons/icon.ico`（原缺失，electron-builder 日志曾报“default Electron icon is used”）

图标用**代码绘制**（`scripts/make-icon.mjs`）：交付物必须可复现且不含任何第三方素材，

接入三处，缺一不可：

|---|---|---|
| `win.icon` + `signAndEditExecutable: true` + `signExecutable: false` | exe 内嵌图标与文件元数据（资源管理器/固定开始菜单） | `(Get-Item FocusNews.exe).VersionInfo` → ProductName/FileDescription=FocusNews，FileVersion=0.1.0（之前是 Electron 默认值） |

| `scripts/check-env.mjs` 新增硬检查 | 图标丢失时不再静默回退默认图标 | `应用图标 6 个尺寸`；缺失或目录项不足 4 个即退出码 1 |

因此 C12 的处置已被取代（保留在 yml 注释里写了退回条件）。
