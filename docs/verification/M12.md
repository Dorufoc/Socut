## M12-A CI 工作流 · 已完成

| 文件 | 触发 | 内容 |
|---|---|---|
| `.github/workflows/verify.yml` | `push`(main/master) / `pull_request` / 手动 | windows-latest + Node 24（下限 22.19，理由见 M12-G）+ npm 缓存 → `npm ci` → 资源引导 → `npm run verify:ci`；失败/成功都把 `spikes/`、`out/` 作为 artifact 上传 |
| `.github/workflows/package-win.yml` | **手动** | 资源引导 → `npm run package:win`（可选 `--verify` 跑安装/升级/卸载冒烟）→ `npm run smoke:packaged:ai`（打包后原生运行时 + 随包模型真实推理烟测）→ 上传 `release/*.exe|.msi` 与 `last-package.json` |

**为什么资源不在 CI 里"随仓库走"**：仓库按纪律不提交二进制（FFmpeg 201MB + 字体），
CI 用 `actions/cache` 缓存 `resources/ffmpeg`、`resources/fonts`、`resources/models/{matte,rnnoise}`，
缓存键 = 对应 fetch 脚本的哈希；缓存未命中时由 `scripts/ci-bootstrap.mjs` 调 `fetch-ffmpeg/fetch-fonts`
取回，取不回则 CI 直接红（不进入 verify）。**两个小模型（RNNoise 296KB + AI matte 452KB）默认也取回**，
下载失败只警告 —— 这样「真模型 / 随包模型」用例在 CI 里真跑而不是 skip。

**`verify:ci` 脚本**（新增）：

```
check:env → eslint → typecheck(node/web/tests) → vitest → electron-vite build
```

与本地 `npm run verify` 的唯一区别是**多了生产构建**：保证 main/preload/renderer 三份产物能编译出来
（打包 workflow 直接吃 `out/`，编译不过的话打包也没有意义）。

**明确不放进 push CI 的东西**
- `verify:all` 的应用内 10 个场景（需要真实窗口/桌面会话；Windows runner 上跑 Electron UI 冒烟不稳定）；
- 真机 GPU 编码器相关断言（CI 无独显，`tests/encodingDelivery.test.ts` 会自动检测随包 FFmpeg 的编码器并跳过）；
- 安装包冒烟（NSIS 安装/升级/卸载，放进手动 `package-win` workflow）。

## M12-E 原生可选依赖（onnxruntime-node）打包 · 已完成（M8-P1 配套）

M8-P1 引入第一个**原生**运行期依赖，打破了"主进程只依赖 electron + node 内置模块"的旧假设，这里记录配套的四件事：

1. **构建**：`electron.vite.config.ts` 主进程 `rollupOptions.external = ['onnxruntime-node','onnxruntime-common']`
   —— 原生 `.node`/DLL 不能被 Vite bundle。
2. **打包**：`electron-builder.yml` 的 `files` 白名单显式带 `onnxruntime-node`（package.json + dist）
   与 `onnxruntime-common`，只带 **win-x64** 的 `onnxruntime.dll` + `onnxruntime_binding.node`，
   排除 darwin/linux/arm64 与 DirectML/dxcompiler（≈36MB GPU EP 本轮不用）；`asarUnpack` 显式解出这两个二进制
   （`process.dlopen` 需要真实路径；实测 electron-builder smartUnpack 会把该可选包整体解到 `app.asar.unpacked`，
   只会是 files 白名单内的 win-x64 文件）。模型走 `extraResources`，属可选资产。
3. **CI**：两个 workflow 的资源缓存加 `resources/models/{matte,rnnoise}`；`ci-bootstrap.mjs` 默认取回这两个小模型
   （296KB + 452KB，失败只警告）；`package-win.yml` 在出包后加一步 `npm run smoke:packaged:ai`。
4. **打包后烟测**：`scripts/smoke-packaged-ai.mjs` / `npm run smoke:packaged:ai`
   —— 用 `release/win-unpacked/Socut.exe` 的 `ELECTRON_RUN_AS_NODE=1` 模式（asar 支持仍开启），
   从 **app.asar 路径** require 原生模块、读随包模型跑一次真实推理。只跑单元测试证明不了
   "装进安装目录后还能 dlopen"，这一步补的就是这个缺口。

实测（本机）：

```
npm run package:win -- --dir --no-open     # 8.2s
# release/win-unpacked/resources/app.asar.unpacked/node_modules/onnxruntime-node/bin/napi-v6/win32/x64/
#   onnxruntime.dll 31,736,672 B / onnxruntime_binding.node 358,200 B
# release/win-unpacked/resources/models/matte/selfie_segmenter.onnx 462,352 B

npm run smoke:packaged:ai
# ✓ asar 主进程入口存在
# ✓ 打包后的 onnxruntime-node 可加载（asar → app.asar.unpacked 重定向正常）
# ✓ 随包 AI matte 模型存在（462352 字节）
# ✓ 打包后真实推理通过：输入 pixel_values → 输出 alphas
# ✓ AI 抠像运行时打包烟测通过
```

**已知取舍 / 风险**：`npm ci` 需要网络（onnxruntime-node 是 optionalDependency，安装期拉 npm 包；
npm 若拉取失败，应用仍能启动，AI 抠像显示「运行时未就绪」）；只带 CPU EP（无 DirectML/GPU 档）；
N-API v6 与 Electron 45 的 ABI 经真实打包烟测验证；Linux/macOS 交叉出包未验证（本项目只交付 Windows x64）。

## M12-G 首次真跑 GitHub Actions · 已完成（2026-11-10 实测）

仓库已发布到 <https://github.com/Dorufoc/socut>（public）。首次 push 触发的 `verify` **是红的**，
修完下面这个问题后第二次全绿 —— 这条正好证明「本机全绿 ≠ CI 全绿」：CI 抓到的是本地环境永远
碰不到的一个**依赖运行时下限**问题。

| 运行 | 触发 | 结果 |
|---|---|---|
| [#42725915595](https://github.com/Dorufoc/socut/actions/runs/42725915595) | 首推（工作流钉 Node 22.12.0） | **失败 2m09s**：`Verify` 步 68 errors |
| [#42726427708](https://github.com/Dorufoc/socut/actions/runs/42726427708) | 修 Node 版本后 | **通过 2m52s** |

### 失败原因：jsdom → undici 8 在 Node 22.12 上加载即崩

表现是「node 池 70 个文件照常跑完、dom 池 68 个文件全部起不来看代码」，每个 dom 文件都报：

```
Error: [vitest-pool]: Failed to start forks worker for test files .../uiStore.test.ts
Caused by: TypeError: Cannot read properties of undefined (reading 'bind')
  ❯ node_modules/jsdom/node_modules/undici/lib/interceptor/decompress.js:78:30
```

`node_modules/jsdom/node_modules/undici` 实际版本 **8.12.3**，`engines.node = ">=22.19.0"`：它在
模块**加载期**就执行 `createZstdDecompress.bind(...)` 去拼 `supportedEncodings` 表，而
`zlib.createZstdDecompress` 是 **Node 22.15** 才引入的。工作流钉 `22.12.0` → 该函数 `undefined` → `.bind` 崩 →
所有 `environment: 'jsdom'` 的用例 worker 起不来。本机是 Node 24.16，所以本机 139 文件全绿，问题只在 CI 暴露。

**修法**（对齐运行时，而不是把测试跳过或加 `continue-on-error`）：
- `verify.yml` 的 `setup-node` 改 `node-version: '24'`（与开发机 24.16、Electron 45 自带的 Node 24 一致），注释写明理由；
- `package.json` 的 `engines.node` 从 `>=22.12.0` 提到 **`>=22.19.0`**（依赖树的真实下限）；
- README 的环境要求同步为 `≥ 22.19`。

## 本地 verify:all 的坑（环境变量，已实测）

`npm run verify:all` 的应用内 10 个场景靠 `electron-vite dev` 拉真实 Electron；如果当前 shell/父进程带着
**`ELECTRON_RUN_AS_NODE=1`**，Electron 会以 Node 模式运行，主进程里 `require('electron')` 拿到的是二进制路径字符串，
启动即崩（`TypeError: Cannot read properties of undefined (reading 'registerSchemesAsPrivileged')`）。
verify:all 的表现是**所有应用内步骤 1 秒内失败 + 「取证文件无法解析」**（CLI/MCP/vitest 步骤仍全绿，容易误判成代码回归）。

```
Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue   # PowerShell
npm run verify:all
```

> 该变量只在手动调试「打包后的 Electron 以 node 模式跑脚本」（如 `npm run smoke:packaged:ai`）时临时设置，
> 不要留在会话环境里。
